# Changelog

All notable changes to Atlas. Atlas follows semantic versioning:
- **Patch** (1.0.x): fixes only.
- **Minor** (1.x.0): additive features, new optional fields, additive migrations. Applied automatically by default.
- **Major** (x.0.0): a migration that needs user input, a non-additive data change, or a breaking change for extensions. Applied after the user says yes.

Each release's "What's new" section is shown to users in the Atlas Guide and their next Daily Brief. "Action needed" lists what only the user can do; each line becomes an "Action needed" item at the top of the next Daily Brief that stays until it's done. "Under the hood" notes are for maintainers and are not shown to users. How to write this file and cut a release: the release checklist, `docs/maintainers/releasing.md` on the upstream repo's `maintainers` branch.

## Unreleased

### What's new
- Atlas no longer warns that it couldn't save to GitHub when everything was saved.
- Updates are checked before they install: Atlas installs a new version only if it was signed by Atlas's maker, and skips (and tells you about) any that isn't.
- Before anything is sent, shared, or deleted from a chat, Claude shows its own approval card with exactly what will happen. Setup now walks you through turning these cards on.

### Action needed
- In Settings → Connectors, set every tool that sends, replies, forwards, shares, or deletes to ✋ **Needs approval**, and remove those connectors from your Atlas routines (routines only draft). Ask Atlas "help me set up approval cards" and it walks you through it.
- Update each Atlas routine's instructions so it stops if it ever runs outside its "Atlas routine" environment. Ask Atlas "update my routine instructions" and it shows you exactly what to paste.

### Under the hood
- Shell guard: commands after a blank line, or after `;` and a newline, were merged into the previous command and missed by the guards (a delete written that way went unseen). Any token made only of separator characters now ends a command. This also fixes `cd` being ignored after heredocs.
- N5: owned paths are never written by editing, in any context. Restoring from an explicitly named `HEAD` is always allowed (the index is never a trusted source); under the update lock, `git checkout` from `refs/atlas-upstream/*` or a commit already in history, and `git rm`. Commits touching owned paths need the lock and `Atlas-Actor: update`. `git fetch`/`pull` reach only origin and `https://github.com/<manifest.upstream>`, one source at a time, and only the upstream may fill `refs/atlas-upstream/*` (checked by the ref's full name). Adding other remotes and redirecting fetches (`url.*`, `remote.*`, `branch -u`) are blocked. A glob with no folder (`rm -rf sys*`) counts as its whole folder.
- Tripwire: send, share and delete are blocked while tracked owned files differ from HEAD, or `.claude/hooks/` has untracked files, outside an update; `atlas-health` restores them with `git checkout HEAD -- <owned paths>`.
- Risk classifier: `collaborator`, `visibility` and `gist` are share words; on GitHub tools, an input setting visibility, privacy or a permission is a share.
- Zip updates removed: releases install only from the upstream tag. `system/tools/build-zip.md` deleted.
- Signed releases: `system/tools/release_check.py` (standard library only; no `ssh-keygen` needed) verifies a release tag's SSH signature against the release keys it carries. `atlas-update` runs it after fetching and before taking any file; the paths hook accepts `refs/atlas-upstream/*` as a source only when the tag passes it (name must match, annotated, signed by a release key).
- Chat approvals: repo hooks don't load in Cowork chats, so the chat-side guard is Claude's confirmation plus Cowork's approval card. Setup step 9 and `atlas-connectors` set send/share/delete tools to Needs approval; routines get no sending connectors; the quarterly review re-checks both. Governance, kernel and Controls guide say where hooks apply.
- Data exits (#6): `git push` goes only to origin, and origin's push URLs must still be this repo (pushurl/pushInsteadOf can't redirect it); `GIT_*` variables are blocked; `gh gist`, `gh repo create/fork`, `gh alias set`/`gh extension`, and `gh api` calls that create gists, forks or repos are blocked; curl/wget that send data (body, form, file, non-GET method, config file, wget `-e`) are a share; in routines, WebFetch, curl and wget reach only the employer's website and email domains (`atlas.yaml: company`; real domains, not shared hosts) and GitHub; export/import/upload tools are a share unless the connector is the user's own storage (`own_storage`, new optional `connectors.yaml` field; a `files` connector counts unless marked `false`).
- Connector writes (#7): GitHub connector calls that write into this Atlas repo (any `path`/`file` key, nested) are blocked for owned paths, protected settings, `.atlas-tmp/` and `.git/`; GitHub writes to another repo, forks and new repos are a share; forced ref updates are blocked (N8).
- Upstream bypass (#12): hooks skip enforcement only when origin is the upstream **and** the git-ignored `.atlas-maintainer` file exists; a clone of the upstream is guarded, and setup tells its user to create their own repo from the template. Atlas never creates, changes or removes that file.
- Routine marker (#5): the routine prompt checks `ATLAS_CONTEXT` first, and a run without `routine` stops before any job (it used to continue by instruction).
- Sync hooks: session start on a non-main branch (cloud routines' `claude/...` branch) fetches and fast-forwards to `origin/main` instead of failing; the end-of-turn check fetches before counting unpushed commits and skips the count if the fetch fails.

## 1.0.0 (2026-10-16)

### What's new
- First public release of Atlas.
- Choose which meetings Atlas shows: all-day events, tentatively accepted meetings, and invitations you haven't answered can each be included or skipped in your brief, Week Ahead, and meeting prep. Everything is included unless you change it, and deadlines on your calendar always show.
- Two new people categories, **prospect** and **board**, and clear definitions for every category so people are sorted the same way every time.
- **Rank your goals.** Tell Atlas which goal matters most, at setup, at the quarterly reset, or any time ("make retention my top goal"). Work tied to your top goals now rises higher in your priorities, and the Goals page lists them in your order.
- **A Week Ahead you can plan with.** It opens with this week's outcomes, a strip showing how full each day is and how much focus time is free, a check of whether that time covers the work you owe, the meetings that need preparing, and anything about the schedule worth fixing early. Select a day to see just that day; select a meeting to see its details and prep.
- **Commitments and Projects pages.** What you owe and what you're waiting on, in two clearly separate sections; and every project with its health, next step, and open commitments and risks.
- **New Records page**: browse and search everything Atlas has filed, by name, type, or status. Select a record to open it in full (details, notes, and linked records you can follow), with a button that copies a request for Atlas when you want to change it. The Commitments, Projects, Decisions & Risks, and People pages open their cards the same way, and so do meetings on the Week Ahead.
- **Atlas learns from your corrections.** When you keep dropping the same kind of "commitment", reranking the same kind of work, or dismissing the same kind of insight, Atlas suggests a rule and follows it once you agree. The monthly report shows what it learned.
- **Playbooks.** Atlas notices work you repeat and offers to save it as a playbook. When one starts, it sets up the checklist with dates, drafts the messages as each step comes due, and flags steps that are missed or out of order.
- **Insights come with the draft.** When an insight suggests messaging someone, the draft is already waiting in your mail.
- **Focus time for what you owe.** When something you owe is due soon and your calendar is filling up, Atlas offers to block time for it (a private hold, only after you say yes).
- **Templates for things you make often.** Atlas offers to turn a recurring deliverable into a template, so every edition is consistent and quicker.
- Atlas checks itself at the start of each chat (that your instructions are current, that it's up to date with your repository, and that it can save to it) and only speaks up if something's wrong, with the fix.
- Every dashboard opens the same way: a one-line headline on what matters most there right now, the key numbers as cards, and when the page was last refreshed, behind a green signal dot that turns amber, with "May be out of date", when a page is older than it should be.
- **Things only you can do come first.** When an update needs something from you, like new Project instructions, it appears at the top of your next Daily Brief under "Action needed" and stays there until it's done. The Control Center shows any text to copy.
- **Coming from another notes app?** Setup asks, then brings your notes in once, first thing after the permission check, so the rest of setup only asks about what your notes didn't cover: from an **Atlas Import** folder in your drive, or an export you attach, zipped or not. Atlas asks what to leave out once it can show you your folders. Notes about you shape your profile after you confirm; everything else becomes connected records with links back to the originals. Atlas never changes your old notes. Open to-dos from the last 60 days stay live. "Undo the import" takes it all back out.

### Under the hood
- Routines use the user's local time: the routine prompt (`system/jobs/README.md`, `atlas-setup` automations §4) and kernel §6 step 1 run `TZ=<atlas.yaml timezone> date` first and ignore the session's stated date, which is UTC. Fixes run dates, file names, and log times recorded in UTC.
- `rhythms.yaml: meetings` (`all_day`, `tentative`, `not_responded`: `include | skip`), optional with `include` defaults; the filter rule lives in `system/schemas/settings.md` and is referenced by the brief, Week Ahead, meeting prep, `atlas-prep`, and `key_meeting_upcoming`. Validator checks the block.
- Event schema: new optional `all_day` (boolean) and `response` (`organizer | accepted | tentative | not_responded | declined`), mapped from Google Calendar and Outlook in the connector hints.
- Person schema: `relationship` adds `board` and `prospect`, with a definitions table and a first-match decision order (§Relationships). People dashboard weights, CRM mapping, the setup interview, `new_key_person`, and the triage priority rubric use them.
- Goal schema: optional `rank` (1 = most important among active goals; user-set only; renumbered on change). Triage's goal-link boost is scaled by rank (`1 − 0.6 × (r − 1)/(N − 1)`; unranked = 0.4 while others are ranked, 1.0 when none are). Validator checks rank values and duplicate ranks; the monthly user health check renumbers gaps. Goals dashboard sorts by rank and shows "#n".
- New built-in dashboard `records` (contract, template, fixture), republished by `maintenance` and `weekly-review`, 1500 KB budget. The record panel is shared (`N.recordPanel`, `N.clickable` in `_base.js`; README §Record panel) and used by Records, Commitments, Decisions & Risks, and People, whose items may carry the same optional panel data (`details`, `body`, `body_truncated`, `links`, `created`, `updated`). Records carry `details` (up to 12 labelled fields) and `body` (plain-text sections, at most 2,000 characters, `body_truncated`; none for sources or summary-handled records) for the record panel; truncation drops bodies before records. Existing users get it at their next chat (a new dashboard missing from `dashboards.yaml` is published then).
- `sync_start.py` adds a `git push --dry-run` write check after the pull and reports a read-only attachment; kernel §2.1 and `sync.md` say to re-attach with write access. Bootstrap stub now asks for "write (push) access".
- Learning loop: `feedback` activity-log lines (`not_a_commitment`, `missed_commitment`, `wrong_close`, `priority_up/down`, `noise`, `insight_useful/noise`), a monthly learning pass (≥3 consistent signals in 60 days → max 3 proposals), confirmed rules in `preferences.md` `## Triage rules` / `## Insight rules`, applied by capture, triage, and insights (`.claude/skills/atlas-triage/reference/learning.md`). Sender/channel noise becomes a proposed data-rule exclusion (approval in chat).
- Playbooks: schema adds `anchor`, `auto_start`, structured `steps` (`step`, `when`, `draft`, `to`); runs are a `task_group` project with one commitment per step; new built-in trigger `playbook_start`; intelligence proposes playbooks from work repeated 3+ times in 12 months; email-drafts pre-drafts communication steps; triage flags out-of-order and skipped steps (`.claude/skills/atlas-triage/reference/playbooks.md`).
- Insight drafts: `Draft for:` / `Draft:` lines on insight entries; `email-drafts` drafts for the top `brief_max` insights; the brief shows "Draft ready".
- Inbox lifecycle: a `counts` block in each inbox file's frontmatter, kept by every writer and checked by the validator; `maintenance` moves entries resolved more than 14 days ago to `user/inbox/archive/YYYY-MM-<name>.md`. History readers (insight engagement, monthly review) include the archive.
- Field formats: `schema.yaml: field_formats` declares ref/refs/list/emails/date/dt/bool/int/steps per field; the validator enforces them; new `system/tools/normalize.py` fixes mechanical problems in place (bare IDs, scalar lists, email case, enum spelling, date-only fields), run on write and by `maintenance`.
- `hot.md` capped at 75 lines: only live, non-closed records (no sources, people, organizations); validator enforces it. New `schema.yaml: closed_statuses` shared by the hot index, the Records page, and the validator.
- Boot check: `system/kernel.md` carries `atlas-kernel-2`, `manifest.yaml` gains `kernel_version` and `bootstrap_version` (validated against the kernel and the bootstrap stub, now "Atlas bootstrap 2"); `sync_start.py` emits one "Atlas boot:" line; kernel §2 step 0 verifies kernel, sync, push, and Project instructions, and reports only failures.
- Source compaction (`source.md` §Compaction): maintenance replaces long bodies of processed sources (30+ days, full retention, >2 KB, not linked from open items) with a summary, an "Extracted into" list, and `full_text_commit`; paths and links never change. Text search skips `sources/` below L4.
- Commitments gain `effort` (`quick | hour | half_day | day`); new built-in trigger `focus_time_needed` proposes a focus block (`own_calendar_manage`, propose) when free time before a due date is under 2× the effort (`.claude/skills/atlas-triage/reference/focus-time.md`).
- Deliverable templates in `user/work/templates/<slug>.md` (formats.md §7), detected from 3+ similar deliverables in 6 months, used by `atlas-write` and status updates; validator checks them.
- Refresh marker: `N.refreshed()` in `_base.js` (masthead, all templates via `render.py --sync`) from `meta.generated_at` (`generated_by` is kept in the data but not shown); contracts gain optional `stale_after_hours` (daily pages 36, weekly 192, About You 768, none for Atlas Guide), copied into `meta` by `atlas-dashboards` and checked by the validator. Masthead shows the Atlas mark and "Atlas" (no user name); the footer shows only the Atlas version (left) and the theme button (right). Pages no longer show record IDs, `[[type/slug]]` citations, inbox entry numbers, or file paths: `N.rid`/`N.path` render nothing, `N.ref` shows the title (linked when `record_base_url` is set), and `N.rich` drops bracketed citations and turns other mentions into readable names. The data still carries every ID. Every page header is title, subtitle, headline (new required `meta.headline`, one sentence written at each render; README §Page header says what each page's headline leads with), then the counts as stat cards. Subtitles: the Daily Brief and Week Ahead show their dates, project pages their summary, and every other page a fixed line saying what it's for (Records: "All your knowledge, in one place."); no "As of" dates. The Goals period moves to the first stat card; the Control Center's status line is its headline. The Work Board is split in two: `commitments` (renamed from `work-board`; Waiting on and I owe sections, filters All / Overdue / High priority) and a new `projects` dashboard (contract, template, fixture; republished by `daily-brief`, `triage`, `weekly-review`; projects carry their open `commitments` and `risks` for the panel, and `page_url` when they have a project page, which their card then opens). Registered in `dashboards.yaml`, the validator, `render.py`, and the nav order; eleven built-in dashboards. Week Ahead adds `outcomes` (from the weekly review's suggested priorities, status refreshed each run), per-day `free_hours`, `summary.focus_hours` / `work_due_hours` / `unsized` (effort-weighted), `watchouts` (overloaded, no_break, double_booked, unprotected_deadline), and `prep.summary` / `prep.todo`, all computed by `atlas-brief`; the headline moves to `meta.headline`. Week Ahead planning data is one procedure (`atlas-brief` §D) used by the daily brief and by the Friday weekly review (next Monday to Sunday). Triage republishes Projects when project health or next steps change; adding or removing a project page republishes Projects. `meta.record_base_url` is removed: pages link only to other dashboards. Daily Brief order: action needed, (catch-up: while you were away), top priorities, today, due and slipping, waiting on others, needs you, worth knowing, drafts ready; every section has a description and no count; "What changed" and "Since last night" are no longer on the page (the brief file keeps them; morning catch-up items appear in their own sections). Notices render as tinted alerts with an icon and a level label; a signal dot (green, amber when stale, grey before the first refresh) leads the refresh marker. Links only open other dashboards: every page shows the same nav row in a fixed order (`meta.nav` lists them all), names of other dashboards in page text link to them (`N.pageLink`), and the Atlas Guide's jump-to-section links are gone. New default palette for users without brand guidelines (`_base.css`): warm stone neutrals (`#f4f0e8` background, `#1c1a15` text), navy accent `#28374a`, rust highlight `#754437`, olive muted `#6b6751`, with dark-mode counterparts; all text pairs pass WCAG AA in both modes.
- Release checklist (`docs/maintainers/releasing.md`), the one place for release steps, kept with the regression suite on the upstream repo's `maintainers` branch so neither ships to users; `build-zip.md`, the tests README, the What's-new guide rules, and the bootstrap stub point to it. No release tags until 1.0.0 ships.
- User actions: changelog releases may carry `### Action needed`; `atlas-update` turns each line, and any rise in `bootstrap_version`, into an open `action` question (new kind) in `user/inbox/questions.md`, deduplicated by `Action key`. Daily Brief shows open actions first (`action_needed` section, uncapped); the Control Center shows `copy_text`. New optional `atlas.yaml: bootstrap_confirmed`, set by setup and by the chat boot check when the Project instructions are current; the boot check opens or closes the `bootstrap` action instead of the old `bootstrap-outdated` known issue. Validator checks `bootstrap_confirmed` and that `CHANGELOG.md` has a section for `system/VERSION` with only known `###` headings.
- Import (`.claude/skills/atlas-capture/reference/import.md`): imported files are never records. Each note becomes a source of the new kind `import` (fields `import_id`, `original_path`; frontmatter kept as plain text), then records through the write path. Routes: a read-only drive folder (excluded in `data-rules.yaml` through a `governance_settings` approval, read once), a chat attachment, or the user's computer; attachments are staged outside the repo and instruction files (`CLAUDE.md`, `AGENTS.md`, `.claude/`, …) are deleted unread. In setup the whole import runs first, as step 6a, before the gather message (6b), research, the interview, connectors, and routines: route, list folders by name, then the leave-out questions (never asked before the notes are listed), map once, batch 1, batch 2 (5-note sample, then chunks of ~25 with resume at step 6). State in `user/.state/import.yaml`. Imported history fires no creation triggers, is no insight or brief change, and gives no learning signals. Undo in `atlas-memory` §G. Control Center shows `system.notes_import`. Validator checks the state file. Called an import, never a migration, so it stays apart from update data migrations.
- Suspicious content (N7, `atlas-capture` §8): an item with instruction-like text aimed at an assistant yields nothing but one flagged source (`retention: summary`, no participants, empty links, body summarized in Atlas's words); no records are created or updated from it and nothing links to it. It's reported in the run report and the Daily Brief. Governance N7, the extraction reference, and `source.md` match; flagged sources are no longer exempt from compaction (they're summaries already).
- Playbooks: a process stated in a source, by the user or someone they work with, is created `active`; only a playbook Atlas infers from recurring work starts as `draft`.
- Daily Brief: "Questions from Atlas" shows questions raised since the last brief first, then the oldest, each linked to its record or source; the template's example lines now carry links.
- Insights link every record they name or put at risk (the risk, each affected project, the goal) and name the dates at stake.
- Provenance: a record whose key field (role, owner, date) is inferred rather than stated in a source is `inferred`, with the inference explained in its body.
- Insights: a risk that only appears when facts from different sources are combined gets its own insight naming both facts.
- Topics: created when a theme recurs across three or more records from at least two sources, linking those records.
- Daily Brief "Waiting on": open `waiting_on` items overdue or due within 7 days (soonest first), plus anything waiting 7+ days without a date, instead of aging items only.
- Routine run reports: counts checked before committing; the run report commit carries any activity-log lines not yet written, and needs none of its own.
- Validator: list-valued enum fields (a source's `flags`) are checked entry by entry, so `flags: [suspicious]` validates.
- All changes are additive: no migration and no `data_version` change. Existing inbox files without a `counts` block get a warning until the next `maintenance` run adds it.
